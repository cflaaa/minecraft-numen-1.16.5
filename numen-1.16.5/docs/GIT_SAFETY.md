# 反思与新的保存方式（GIT_SAFETY）

> 起因：2026-10-13 下午，一次普通的刀 5 收尾改造过程中，**工作树的 `core/src` 整个目录
> （379 个文件）从磁盘消失**，其中 **21 个文件**因被 `.gitignore` 误忽略而**从未进过版本库**，
> 只能靠「反编译已部署的 jar」才救回来。
>
> 本文做两件事：① 把问题想清楚（为什么会发生、为什么会不可恢复）；② 定下新的保存规矩与工具，
> 目标是**模型报错中断**与**误删除**都不再造成不可逆损失。

---

## 一、事故经过（事实）

1. 实现刀 5 的 @Fn 收尾：新增 `WorldTools`、改写 6 个文件、`git rm` 掉 3 个自写件。
2. `git rm` 执行后，`core/src` **整个目录从磁盘消失**（379 文件：370 编译单元 + 2 个包目录 + …）。
   **直接诱因至今不明**（无 hook、无别名、`core` 不是软链；疑似环境瞬时故障）。
3. `git restore --worktree` 从索引恢复 370 个文件 → **编译仍失败**：缺 `core.build`、`core.task.build` 两个包。
4. 查出这两个包的文件 **在 git 索引里根本不存在** —— 被 `.gitignore:23` 的 `**/build/` 连坐忽略，
   **从来没有被提交过**。
5. 抢救：从**已部署 jar**（`.testserver/mods/numen-0.1.4-1.16.5.jar`，刀 4 构建）反编译恢复 21 个文件
   （抽 class → tiny-remapper intermediary→named → CFR → 剥冗余强转 → 文本重映射残留名 → 修 5 处反编译产物）。
6. 编译恢复绿；修复 `.gitignore`；恢复成果提交 `32c2280`。

## 二、为什么会「不可恢复」——三层原因

| 层 | 问题 | 本次的代价 |
|---|---|---|
| **① 忽略盲区** | `**/build/` 这种通配把**源码里真叫 `build` 的包**一起忽略了 → 那 21 个文件 git 从没见过 | 无法从 git 恢复，只能反编译 |
| **② 未提交窗口** | git 只保护**已提交**的东西。一刀之内攒了几小时的改动（新增文件 + 6 处改写 + 3 处删除） | 刀 5 的改动被整体打回 HEAD，全部重做 |
| **③ 单点目录损毁** | 379 个文件一次性消失，**诱因不明** | 无法预防，只能靠"任何状态都可回滚"兜底 |

> ② 和 ③ 是**流程**问题，① 是**规则**问题。规则问题可以一次性修掉并自动化防住；
> 流程问题只能靠"把不可恢复的窗口缩到最小"来缓解。

## 三、暴露出的流程缺陷（这是最该改的）

1. **"验证过了才提交，一次一刀"这条好规矩被误用成了"攒一大批再提交"。**
   一刀之内可以有几小时的工作量，中间没有任何备份点——一旦出事，全丢。
   原规矩想保证的是**历史干净**，并不要求**中间状态无备份**；这两件事可以兼得（见 R2）。
2. **加通配 ignore 规则前从不体检**：没人问过"源码树里有没有叫 `build` 的目录"。
3. **可复用脚本长期躺在 `.workbuddy-ai/tmp/`**（被忽略）：搬运脚本 `port-knife4.py`、重映射 `k5remap.py`、
   全套 e2e 验收脚本——这些是"怎么把这事再做一遍"的知识，却不在版本库里（只有快照覆盖）。
4. **没有"动手前先快照"的习惯**。事故发生时手上有一堆未提交改动，没有任何一份可用备份。

## 四、新的保存规矩（写死，按这个做）

> 配套工具在 `tools/`（**已入库**）。钩子由 `python tools/install-hooks.py` 装一次，
> 之后每次提交自动跑审计。换机器/重新 clone 后重跑安装器即可。

### R1 快照先行 —— 碰很多文件之前，先打快照
凡是可能大面积改动/删除的操作，**动手前**先跑：

```bash
python tools/git-snapshot.py            # 备份到仓库外 ../我的世界-backup/snapshot-<时间戳>/
```

**必须快照的操作**：`git rm` / `git clean` / `git reset`、批量改写或搬运脚本（`port-*.py`、`fix-*.py`）、
反编译流水线、以及任何"一次性动几十个文件"的步骤。
快照内容：`repo.bundle`（全部 ref 的历史）+ `worktree.tar.gz`（**工作树原样，含未提交、未跟踪、被忽略的脚本**）
+ `STATUS.txt`（当时的 git 状态与最近 8 次提交）。默认轮换保留 12 份（`--keep`）。

### R2 检查点提交 —— 一刀之内，编译一绿就落一个 WIP 提交
不再"攒到验收才提交"。**每当 `:core:compileJava` 绿了，就提交一个 WIP**：

```bash
git add -A && git commit -m "WIP: <这一步做了什么>"
```

一刀做完、真机验收通过后，把这串 WIP **压成一个刀提交**，历史仍然"一次一刀"：

```bash
git reset --soft <这一刀开始时的提交>     # 改动回到暂存区，历史退回
git commit -m "刀 N：<正式提交信息>"      # 重新提成一个干净提交
```

这样：**中间状态始终有备份**（中断、误删都能回到最近的绿点），**最终历史仍然干净**。
快照是兜底，WIP 提交是常规；两者都要有。

### R3 通配 ignore 必须先体检 —— 现在由钩子自动拦
- 加/改 `.gitignore` 后，必须 `python tools/git-audit.py` 干净（退出码 0）。
- `pre-commit` 钩子每次提交自动跑，有 SUSPECT **直接拦住提交**。
- `git-audit.py` 用中文会说法的规则也已修：`core.quotePath=false`（否则 `accept-刀4.py` 这种中文文件名认不出来）。

### R4 可复用脚本进 `tools/`（入库），一次性的才留 `.workbuddy-ai/tmp/`
判断标准：**"三个月后还想照着再做一遍吗？"** 想，就进 `tools/`；一次性调试脚本留 `tmp/`。
现有 `tmp/` 里 43 个脚本已被快照覆盖，可作为逐步搬迁的候选（搬迁时注意脚本内部互相 import 的路径）。

### R5 模型报错/重启回来之后：先体检，再继续
中断后的第一个动作不是继续干活，而是：

```bash
git status                 # 树里有什么、丢了什么
python tools/git-audit.py  # 有没有「该入库却被忽略」的隐患
```

确认工作树完整（必要时 `git restore --worktree -- <路径>`）再动手。

### R6 恢复路径（真出事时怎么用）
1. **工作树被误删**：`git restore --worktree -- <路径>`（从索引恢复已跟踪文件）。
2. **已提交的改动被 `reset` 掉**：`git reflog` 找到那个提交 → `git reset --hard <sha>`。
3. **连 reflog 都救不了（工作树整体损毁、有未提交改动）**：从快照恢复——
   `tar -xzf worktree.tar.gz`（工作树原样）+ `git bundle verify repo.bundle` / `git clone repo.bundle`（历史）。
   快照在仓库外（`../我的世界-backup/`），**不会跟着仓库一起坏**。

## 五、当前防线清单（已落地）

| 防线 | 位置 | 作用 |
|---|---|---|
| `.gitignore` 放行 `!**/src/**/build/` | `.gitignore` | 源码里的 `build` 包重新入库（已提交 `32c2280`） |
| 可见性审计 | `tools/git-audit.py` | 报出「被忽略却该入库」的文件；中文文件名也能认 |
| 一键快照 | `tools/git-snapshot.py` | 历史 + 工作树原样备份到仓库外，自动轮换 |
| 提交前钩子 | `tools/install-hooks.py` → `.git/hooks/pre-commit` | SUSPECT 直接拦住提交 |
| 一次一刀 | 变更规则 | 一刀内可多次 `WIP:` + 收尾 `reset --soft` 压成一个（本仓规矩） |

> ⚠️ 钩子装在新 clone / 新机器上要重跑：`python tools/install-hooks.py`
