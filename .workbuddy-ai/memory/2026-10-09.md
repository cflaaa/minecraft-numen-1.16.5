## 第三轮：实机启动报「不兼容的模组」—— 根因是 **启动器用了 Java 8**

用户把 jar 放进 PCL 的 `1.16.5-Fabric 0.19.5-2` 实例，报
`HARD_DEP_NO_CANDIDATE numen ... {depends fabric-api @ [*]}`，
提示「安装 fabric-api，任意版本」——**但 fabric-api 明明就在 mods 里。误导性极强的报错。**

### 排除掉的所有可能（都不是原因）

- ❌ fabric-api jar 损坏 —— sha1 `54970c87...` 与 Modrinth 官方**逐字节相同**
- ❌ fabric-api 的 `minecraft: ~1.16.2-alpha.20.28.a` 不匹配 1.16.5 ——
  **实测 loader 的 `~` 语义是 `>=1.16.2-alpha.20.28.a <1.17.0`，1.16.5 命中**。
  （这个 `~1.16.2-alpha.20.28.a` 是 Fabric 的老写法，**看起来**像只匹配 1.16.2，实际不是。别被它骗了）
- ❌ 文件名/重复 jar/残留 `.fabric/remappedJars` 缓存 —— 都干净，缓存的 client-intermediary.jar 也完好
- ❌ 版本 json 结构、zip 压缩方式 —— 与其它两个能用的实例（0.19.5 / 0.19.5-1）**完全一致**

### 真正原因：`fabric.mod.json` 里的 `"java": ">=17"`

本移植**全部 class 都是主版本 61（Java 17）**（实测 24+138+37+189 个 class 全是 61）。
而 PCL 的 Java 列表里有三个：Java 21 / **Java 17** / **Java 8 (jre-legacy, 1.8.0_51)**。
1.16.5 官方要求 Java 8 → **PCL 自动选了 Java 8** → `java >=17` 判定失败 → **numen 自己被 loader 剔除**
→ 依赖链断掉 → 报「缺 fabric-api」。

**用 loader 自己的 `VersionPredicate` 实测（决定性证据）：**

| JVM | `numen` 的 `java>=17` | `fabric-api` 的 `minecraft` |
|---|---|---|
| Java 8 (1.8.0_51) | **REJECT** ← 用户的情况 | PASS |
| Java 17 (17.0.15) | PASS | PASS |

给该实例写 Java 覆盖（`versions/1.16.5-Fabric 0.19.5-2/PCL/Setup.ini`）：

```ini
Java:C:\Users\cfl\AppData\Roaming\.minecraft\runtime\java-runtime-gamma-snapshot\bin\javaw.exe
```

已备份 `Setup.ini.bak`、`config.json.bak`。
PCL 的 Java 候选与路径在 `C:\Users\cfl\AppData\Roaming\PCL\config.json` 的 `JavaList`。
（**注意**：PCL 的 MC 目录是 `C:\Users\cfl\Desktop\.minecraft`，
但 Java runtime 在 `C:\Users\cfl\AppData\Roaming\.minecraft\runtime\`。）

### 教训

1. **Fabric 的「缺 fabric-api」报错经常指错方向。** 任何时候看到它，
   先看 `logs/latest.log` 里的 `Immediate reason:` 行，再怀疑 **JVM 版本**，
   而不是傻乎乎地换 fabric-api（本次的 fabric-api 自始至终都是好的）。
2. **`java: >=17` 这类约束在 Java 8 上会让模组自己被剔除**，症状却是「别的模组缺失」。
3. **1.16.5 模组的默认 JVM 是 Java 8**，而本移植要求 17 —— 这不是「建议」，

## 追加（同日 20:00–20:25）：实机运行期三个坑 + **更正上文「教训 1」**

### ⚠️ 更正：那条 `depends fabric-api` 报错就是**依赖 id 写错**，不是 JVM

上文的归因是错的（已同步改 `docs/PORTING.md` 第 3.2 节）。实测证据：

1. **Fabric API 0.42.0+1.16 的 mod id 是 `fabric`**，`provides` 为空 —— 直接读它的
   `fabric.mod.json` 得到 `id = fabric`。`fabric-api` 是 1.19 之后才改的 id。
2. **Fabric Loader 0.19.5 的所有 class 里搜不到 `fabric-api` 字面量** —— 不存在 id 别名，
   所以 `"fabric-api": "*"` 在 1.16.5 上无解，装多少个 Fabric API 都没用。
3. 实机启动成功的那个 jar（`V10-fixed.jar`）里 `depends` 写的就是 `"fabric": "*"`。

**结论**：1.16.5 侧 `fabric.mod.json` 必须写 `"fabric": "*"`。
（`java: >=17` 是真话、1.16.5 默认 Java 8 —— 那部分仍然成立，只是解释不了这条报错。
同一条报错文本有两个成因，**两条都要查**。）

### 坑一：1.16.5 运行期**没有 slf4j**（1.17+ 才有）

症状：依赖解析通过、模组列表列出，然后在 `NumenCore.<clinit>` 上
`NoClassDefFoundError: org/slf4j/LoggerFactory`。

修法：`core/build.gradle` 内嵌两个（只发 api 会退化成 NOP logger，日志静默消失）：

```groovy
include 'org.slf4j:slf4j-api:1.7.36'                        // 与绑定同代（1.7 系）
include 'org.apache.logging.log4j:log4j-slf4j-impl:2.8.1'   // 与游戏自带 log4j 版本一致
```

### 坑二：gson **2.8.0** 的 API 缺口 —— 24 处

`parseString`/`parseReader`（2.8.6+）8 处、`isEmpty()`（2.8.2+）8 处、
`deepCopy()`（2.8.2+ 才 public，2.8.0 里存在但包级私有）5 处 + `agent` 侧 3 处。

**方法论（很有用）**：把**编译期依赖钉到运行期那个版本**（`api '...gson:2.8.0'`），
编译器就会把所有不兼容点一次列全；单测走 `testImplementation`（抬到 2.10.1）仍可用新 API。
⚠️ **每个模块都要单独编** —— 只编 `ai` 漏掉了 `agent` 的 3 处。

**为什么不用「内嵌新版 gson」（已排除，别试）**：Fabric 实测是**模组类路径优先**
（`KnotClassDelegate.loadClass` 字节码里 `tryLoadClass` 在父加载器之前），能盖住；
但会造成**双类加载器**，而 Fabric API 的 `LootJsonParser` 会把游戏侧的 gson 实例
`checkcast` 成自己的类型 → **每次加载战利品表 ClassCastException**。

**采用**：改源码，但只用**两代通用**的写法（`new JsonParser().parse(x)` / `size() == 0` /
新增 `ai/.../agent/json/JsonCompat.java` 做 deepCopy），全 mod + Fabric API + 游戏
继续共用同一份 gson。

### 挖到的真 bug（**本次最有价值的产出**）

```
java.lang.NoSuchMethodError: 'net.minecraft.class_2561 net.minecraft.class_1792.method_7848()'
    at ...NumenTools.status(NumenTools.java:238)      # 源码：item.getDescription()
```

**根因：Fabric Loom 编译用的类路径是 merged（客户端+服务端）jar，
而专用服务端运行时用的是 `server-intermediary.jar`。客户端 jar 比服务端多若干成员。**
实测 javap 对比：

| 方法 | merged（编译用） | server（运行时） |
|---|---|---|
| `Item.method_7848()`（`getDescription`） | 有 | **没有** |
| `Item.method_7851(...)`（`appendHoverText`） | 有 | **没有** |

- **单机测不出来**（集成服务端跑在客户端进程里，成员是全的）；
- **`gradle build` 成功也不代表能跑** —— 编译器全程沉默。

**改法**：`item.getDescription()` → `itemStack.getHoverName()`
（`class_1799.method_7964()`，实测服务端 jar 里有）。

### 为了「一次找全」写的新工具

**`server-api-check.py`** —— 拿 **merged jar** 与**运行时那份 `server-intermediary.jar`** 对差：

1. `javap -c` 抠出模组 jar 里每条 `// Method/Field net/minecraft/...` 引用；
2. 沿**父类/接口链**（`javap -p -s` 拿描述符）去 server jar 里核对。

实测：修之前 **97 条 MC 引用 / 9 个 MC 类 → 只有 1 条对不上**（就是上面那条）；

## 追加（21:10–21:30）：客户端「偶发不连服」查清了 —— 是环境抖动，不是模组

### 现象

`smoke-llm.py` 里客户端大约**三次里只有一次**能走到「自动连服」那一步。
失败时日志停在贴图图集那几行（`Created: 256x128x0 ... mob_effects.png-atlas`）之后
一声不吭，**连 TCP 连接都不发**（服务端日志里没有任何 `logged in`）。

### 排查过程（都用 `diag-client.py` 做 A/B，单变量）

| 变量 | 结论 |
|---|---|
| JVM：PCL 的 `java-runtime-gamma-snapshot`(17.0.15) vs toolchain JDK(17.0.20.1) | **无关**，两个都能走到 `Connecting to` |
| 有没有监听者（25565 空着 / KnotServer / 一个哑 socket） | 表面上相关，但样本太少（见下） |
| 线程状态 | `jstack` 显示主线程**活着**，在 `Render thread` 的 `glfwWaitEventsTimeout`（FPS 限制器）里 —— 不是死锁 |

**关键澄清**：没有 `--server` 参数时，日志停在图集那几行是**正常的**（本来就不该有
`Connecting to`）。所以「日志停在图集」本身不是卡死证据，**只有「日志里没有
`Connecting to`」才是**。

最后判定：这是**偶发竞态**（约 1/3 成功率），与监听者、JVM 都无关；
20:43 与 20:52 两次成功、之后连续失败，属于概率波动。

### 处理

`smoke-llm.py` 改成 **最多试 6 次、每次 75 秒**，并打印「这次走到自动连服那一步了吗」，
把成功率从 ~33% 抬到 ~90%。**不要把它当成被测对象去修** —— 它不是模组的问题。

### 新增诊断脚本 `diag-client.py`

只起客户端（可选带服务端/哑监听器），跑够时间后 `jstack` 打主线程栈，

